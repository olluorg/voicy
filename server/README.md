# voicy — речевой сервер

Локальный сервер синтеза и распознавания речи с **API, совместимым с аудио-частью
OpenAI**. Любой код, который уже умеет обращаться к `/v1/audio/speech`
и `/v1/audio/transcriptions`, работает с ним после смены базового адреса —
и больше ничего менять не нужно.

Всё исполняется на своей машине. Ключ не проверяется, потому что ключа нет.

## Быстрый старт

**Готовым образом** — репозиторий не нужен:

```bash
docker run --gpus all -p 8080:8080 \
  -v voicy-models:/cache \
  -v voicy-voices:/app/server/voices \
  ghcr.io/olluorg/voicy:latest
```

Или через compose, где уже прописаны тома, перезапуск и GPU:

```bash
curl -O https://raw.githubusercontent.com/olluorg/voicy/master/compose.yml
docker compose up -d
```

**Из исходников:**

```bash
uv venv --python 3.12 .venv
uv pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu128
uv pip install -r server/requirements.txt

python -m uvicorn app:app --host 0.0.0.0 --port 8080 --app-dir server
```

Веб-консоль — на `http://localhost:8080`.

Модели грузятся при первом обращении и остаются в памяти: Qwen3-TTS занимает
около 3.5 ГБ, Whisper — около 1.5 ГБ. В контейнере они складываются в том `/cache`,
поэтому скачиваются один раз и переживают пересборку образа.

## Переменные окружения

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `TTS_MODEL` | `Qwen/Qwen3-TTS-12Hz-1.7B-Base` | модель синтеза |
| `STT_MODEL` | `large-v3-turbo` | модель распознавания |
| `FORCE_CPU` | — | `1` — не использовать GPU |
| `TTS_DEVICE` / `STT_DEVICE` | автоопределение | явное устройство |
| `STT_COMPUTE_TYPE` | `float16` на GPU, `int8` на CPU | точность распознавания |
| `HF_ENDPOINT` | — | зеркало Hugging Face при медленной загрузке |
| `HF_HOME` | `/cache/huggingface` | куда складывать веса |
| `VOICY_QUEUE_MAX` | `32` | сколько заданий может ждать; дальше — 429 |
| `VOICY_JOB_TTL` | `1800` | сколько секунд помнить готовое задание |
| `VOICY_API_KEY` | — | ключ доступа к `/v1/`; несколько — через запятую |
| `VOICY_PUBLIC_URL` | — | адрес снаружи за обратным прокси, для ссылок в заданиях и webhook |
| `VOICY_WEBHOOK_SECRET` | — | ключ подписи webhook, HMAC-SHA256 |
| `TURN_MODEL_FILE` | `smart-turn-v3.2-cpu.onnx` | файл модели конца реплики из `pipecat-ai/smart-turn-v3` |

## Веб-консоль: два режима

**Просто** — большое поле для текста и одна кнопка «Озвучить», плюс перетаскивание
файла или запись с микрофона для распознавания. Ничего настраивать не нужно.

**Подробно** — голос, язык, формат, темп, сид, применение словаря произношений,
статистика синтеза; для распознавания — язык, формат ответа, температура,
подсказка контекста, отметки времени по словам и таблица сегментов. Плюс
управление голосами и готовые примеры кода.

Режим запоминается между заходами.

## Совместимые маршруты

| Маршрут | Что делает |
|---|---|
| `POST /v1/audio/speech` | текст → аудио: `model`, `input`, `voice`, `response_format`, `speed`, `stream_format` |
| `POST /v1/audio/transcriptions` | аудио → текст: `file`, `model`, `language`, `prompt`, `response_format`, `temperature`, `timestamp_granularities`, `stream`, `context`, `hotwords` |
| `POST /v1/audio/translations` | аудио → текст по-английски |
| `GET /v1/models` | список моделей |

Форматы ответа синтеза: `wav`, `mp3`, `opus`, `flac`, `aac`, `pcm`.
Форматы расшифровки: `json`, `text`, `verbose_json`, `srt`, `vtt`.

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8080/v1", api_key="not-needed")

client.audio.speech.create(model="tts-1", voice="turgenev",
                           input="Текст", response_format="opus"
                           ).stream_to_file("out.opus")

with open("out.opus", "rb") as f:
    print(client.audio.transcriptions.create(model="whisper-1", file=f).text)
```

Каждый такой вызов — тоже задание в общей очереди (см. ниже). Снаружи он
синхронен как прежде, а id задания приходит в заголовке `X-Job-Id`; сколько
вызов простоял в очереди — в `X-Queue-Seconds`.

`stream=true` у расшифровки отдаёт текст по мере распознавания, в той же форме,
что и OpenAI: события `transcript.text.delta`, затем `transcript.text.done`.
У OpenAI поток есть только у новых моделей, здесь дельта — сегмент Whisper,
и в ней же указано, до какой секунды файла дошло распознавание. Если клиент
отключился, не дочитав, задание отменяется.

```bash
curl -sN localhost:8080/v1/audio/transcriptions -F file=@запись.opus -F stream=true
```

`stream_format` у синтеза — тоже параметр OpenAI. `"audio"` отдаёт звук кусками
по мере синтеза (`pcm`, `wav`, `mp3`), `"sse"` — события `speech.audio.delta`
с base64 и в конце `speech.audio.done`. Без параметра синтез идёт целиком,
как раньше. Подробнее — в разделе про синтез потоком.

```python
with client.audio.speech.with_streaming_response.create(
        model="tts-1", voice="turgenev", input="Длинный ответ…", response_format="pcm",
        extra_body={"stream_format": "audio"}) as r:
    for chunk in r.iter_bytes():
        play(chunk)                             # PCM s16le, 24 кГц, моно
```

### Ошибки

Ошибки приходят в формате OpenAI, поэтому официальные клиенты показывают
их как свои — `BadRequestError`, `AuthenticationError`, `RateLimitError`:

```json
{"error": {"message": "unknown voice 'x'", "type": "invalid_request_error",
           "param": null, "code": null}}
```

Ошибка в параметрах — 400, как у OpenAI, а не 422, как у FastAPI по умолчанию.
Файл, который не удалось декодировать как звук, — тоже 400: виноват вход,
а не сервер. 500 означает, что сломался сам сервер.

## Доступ по ключу

По умолчанию сервер открыт: на localhost не от кого закрываться. Если порт
виден другим — а в docker сервер слушает `0.0.0.0`, — задайте ключ:

```bash
VOICY_API_KEY=секрет ./voicy up                 # или в .env рядом с compose.yml
VOICY_API_KEY=один,другой ./voicy up            # несколько ключей через запятую
```

После этого все маршруты `/v1/`, включая WebSocket, требуют
`Authorization: Bearer <ключ>` — ровно то, что шлёт `OpenAI(api_key=...)`.
Браузер не умеет ставить заголовок на `EventSource` и WebSocket, поэтому
принимается и `?api_key=<ключ>`; заголовок всё же лучше, строка запроса
попадает в журналы.

Открытыми остаются `/health` (его проверяют docker и CLI), консоль и её статика.
Консоль сама спросит ключ при первом отказе и запомнит его в браузере. CLI берёт
ключ из той же переменной `VOICY_API_KEY`.

Без ключа HTTP отвечает 401 в формате OpenAI, WebSocket закрывается до принятия —
клиент видит 403.

## За обратным прокси

Сервер можно поставить за nginx, Caddy или Traefik — с HTTPS, в корне домена
или под префиксом. Но прокси «по умолчанию» ломает половину API, и ломает тихо.
Проверено на nginx 1.24, одинаковыми запросами напрямую и через прокси:

| Что | Прокси «как обычно» | Что чинит |
|---|---|---|
| загрузка аудио больше 1 МБ | 413 | `client_max_body_size` |
| синхронный синтез дольше 60 с | 504 | `proxy_read_timeout` |
| живая речь и синтез по WebSocket | 404 | заголовки `Upgrade` и `Connection` |
| ссылки в заданиях и webhook | ведут на внутренний `127.0.0.1:8080` | `VOICY_PUBLIC_URL` |
| поток синтеза, события заданий, `stream=true` | работают | — |

Потоки работают и без настройки: сервер помечает их заголовком
`X-Accel-Buffering: no`, и nginx не копит их в буфере. Простаивающий WebSocket
тоже не обрывается: сервер пингует его каждые 20 секунд, и сокет синтеза
пережил 70 секунд молчания за прокси с таймаутом 30 секунд — без пингов
со стороны клиента, как было бы у браузера.

### nginx

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 443 ssl;
    server_name voice.example.com;
    # ssl_certificate …; ssl_certificate_key …;

    client_max_body_size 200m;          # записи на распознавание, образцы голосов

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Upgrade $http_upgrade;             # WebSocket
        proxy_set_header Connection $connection_upgrade;
        proxy_buffering off;                                # поток звука — сразу
        proxy_read_timeout 1800s;                           # синтез длинного текста — минуты
        proxy_send_timeout 1800s;
    }
}
```

**Под префиксом** — тот же блок с косой чертой в `proxy_pass`, она срезает
префикс, и перенаправлением с адреса без косой черты:

```nginx
location = /voicy { return 301 /voicy/; }
location /voicy/ {
    proxy_pass http://127.0.0.1:8080/;
    # … те же proxy_set_header и таймауты
}
```

Консоль ходит по относительным путям и работает под префиксом сама. Но открывать
её нужно с косой чертой на конце: с `/voicy` относительный путь уйдёт в `/v1/`
мимо префикса — для этого и перенаправление.

### Что ещё настроить

**`VOICY_PUBLIC_URL`** — адрес, под которым сервер виден снаружи, вместе
со схемой и префиксом: `https://example.com/voicy`. По нему строятся ссылки
в сводках заданий и в webhook. Без него ссылки берутся из запроса, и за прокси
это внутренний адрес, по которому получатель webhook не достучится. uvicorn
умеет брать схему и хост из `X-Forwarded-*` сам, но верит им только от
`127.0.0.1` — а из docker прокси виден с другого адреса, — и о префиксе
не знает вовсе. Одна переменная надёжнее.

**HTTPS для микрофона.** Браузер даёт микрофон только странице с HTTPS или
на localhost. Консоль на другой машине по `http://` откроется, но «Записать
с микрофона» и «Диктовка» откажут. WebSocket консоль переключает на `wss://`
сама, когда страница открыта по HTTPS.

**Ключ — заголовком.** `?api_key=` попадает в журнал доступа прокси вместе
со строкой запроса. Консоль вынуждена так делать для `EventSource` и WebSocket;
свои клиенты пусть шлют `Authorization: Bearer`, а журнал прокси стоит писать
без аргументов запроса или не писать для `/v1/`.

**Сжатие.** Если в прокси включено сжатие ответов, `text/event-stream` и звук
из него стоит исключить: сжиматель копит данные, и поток приходит рывками.
У nginx по умолчанию проксируемые ответы не сжимаются.

**Cloudflare и похожие CDN** обрывают ответ, который не начался за 100 секунд.
Синхронный синтез длинного текста молчит до самого конца — для таких текстов
берите задания (`/v1/jobs/speech`) или `stream_format`: первые байты там идут
через секунды.

**Caddy** здесь не проверялся. По его документации `reverse_proxy 127.0.0.1:8080`
сам пробрасывает WebSocket и заголовки и не ограничивает размер запроса;
чтобы звук не копился в буфере, добавьте `flush_interval -1`. Прогоните
проверку из таблицы выше, прежде чем полагаться на это.

## Очередь и задания

Обе модели делят одну видеокарту, поэтому работу выполняет один воркер,
по очереди, в порядке поступления. Любой запрос — задание с id: совместимые
маршруты ставят его в очередь и ждут за вызывающего, маршруты `/v1/jobs`
отдают id сразу. Почему так — [ADR 0017](../docs/adr/0017-one-queue-for-every-request.md).

| Маршрут | Что делает |
|---|---|
| `POST /v1/jobs/speech` | то же тело, что у `/v1/audio/speech`, плюс `webhook_url`; отвечает 202 и сводкой задания |
| `POST /v1/jobs/transcribe` | `file`, `language`, `prompt`, `temperature`, `word_timestamps`, `task` (`transcribe`/`translate`), `webhook_url` |
| `GET /v1/jobs` | все задания и состояние очереди; `?state=queued` — отбор |
| `GET /v1/jobs/{id}` | сводка: `state`, место в очереди, прогресс, ссылки, доставка webhook |
| `DELETE /v1/jobs/{id}` | отмена: из очереди — сразу, во время работы — на ближайшем шаге |
| `GET /v1/jobs/{id}/events` | поток событий, `text/event-stream`; смотреть могут несколько клиентов |
| `GET /v1/jobs/{id}/audio` | готовый звук |
| `GET /v1/jobs/{id}/result` | готовая расшифровка; `?format=srt` и другие форматы расшифровки |

Состояния: `queued` → `running` → `done`, `error` или `cancelled`. Пока задание
ждёт, `position` в сводке и `queue_position` в событиях `queued` говорят,
сколько заданий выполнится раньше; при каждом старте очередного число обновляется.

```json
{"id":"8f28fa14e68d","kind":"transcribe","state":"queued","position":2,
 "links":{"self":".../v1/jobs/8f28fa14e68d","events":".../v1/jobs/8f28fa14e68d/events"}}
```

Задания хранятся в памяти: готовые забываются через 30 минут (`VOICY_JOB_TTL`),
а перезапуск сервера забывает все. Очередь ограничена 32 заданиями
(`VOICY_QUEUE_MAX`); сверх этого сервер отвечает 429 с `Retry-After`.

### Webhook

С `webhook_url` сервер сам сообщит о конце задания — успешном, упавшем или
отменённом — POST-запросом со сводкой задания и полем `event`: `job.done`,
`job.error`, `job.cancelled`. Звука в уведомлении нет, только ссылка
`links.audio`: получатель часто хочет знать лишь, *что* готово, а мегабайты
в теле делают каждую повторную попытку дорогой. Расшифровка приходит текстом
в `result.text`, сегменты — по `links.result`.

Ответ 2xx — доставлено; иначе повтор через 2, 10, 30 и 120 секунд. Итог
виден в сводке задания, в поле `webhook`. С `VOICY_WEBHOOK_SECRET` тело
подписывается:

```
X-Voicy-Signature: sha256=<hex HMAC-SHA256 сырого тела>
```

```bash
curl -s localhost:8080/v1/jobs/speech -H 'Content-Type: application/json' \
  -d '{"input":"текст","response_format":"opus","webhook_url":"http://my-service/voicy"}'
```

### Прогресс

**Числа не выдуманы, и там, где это не так, стоит пометка.**

У распознавания точны обе величины: длительность файла известна до начала работы,
а каждый сегмент сообщает, где он закончился. Плюс текст приходит по частям,
не дожидаясь конца.

```json
{"stage":"recognition","position":93.9,"total":171.0,"text":"Случай второй зеркальный."}
```

У синтеза измеряется числитель. Публичный API модели не отдаёт звук по кускам —
в её документации прямо сказано, что режим потока лишь имитирует потоковый ввод
текста, — но внутри модель делегирует работу обычной модели transformers, и в этот
вызов можно подсадить счётчик шагов декодирования. Он ничего не меняет в выводе
и вызывается ровно раз на шаг.

Один шаг — один аудио-токен. Название модели обещает 12 Гц, но на готовом звуке
измеряется 12.6–13.0 шага на секунду: несколько шагов уходит на промпт
и завершение. Взято измеренное значение, а не заявленное.

```json
{"stage":"synthesis","steps":125,"produced":9.92,"expected":13.1,"elapsed":36.1}
```

`produced` — измерение, `expected` — оценка по числу слогов, потому что полная
длительность неизвестна, пока генерация не закончится. В консоли полоса такого
прогресса заштрихована и подписана «оценка», а рядом с распознаванием стоит «точно».

## Свои маршруты

| Маршрут | Что делает |
|---|---|
| `GET /v1/voices` | список голосов и голос по умолчанию |
| `POST /v1/voices` | добавить голос: `file`, `name`, `text`, `note`, `replace` |
| `WS /v1/audio/transcriptions/stream` | живая речь для голосового агента: начало, текст, конец реплики |
| `POST /v1/text/prepare` | применить словарь произношений и убрать запятые внутри коротких фраз |
| `GET /health` | состояние моделей, устройство, список голосов |

У синтеза есть два расширения сверх контракта OpenAI: `prepare` применяет словарь
произношений, `legato` убирает запятые внутри коротких фраз. Оба по умолчанию
выключены — вызывающий ожидает получить свой текст, а не переписанный.

## Голоса

Голос — это короткий образец записи и **его точная расшифровка**. Модель клонирует
по этой паре, и расшифровка важнее, чем кажется: тот же клип с текстом, обрезанным
на полуслове, дал 7.3% ошибок против 1.0% при точном совпадении.

Поэтому при добавлении голоса расшифровку можно не писать — сервер распознает её
сам, и это надёжнее ручного ввода.

Два голоса поставляются готовыми, оба отобраны замером из записей в общественном
достоянии (LibriVox): `turgenev` — 118 слов/мин, слитная манера, выбран из 35 окон
одной записи; `dostoevsky` — 100 слов/мин, чуть больше пауз.

Требования к образцу: 8–14 секунд, чистая запись, начало и конец на границе фразы.

Формат образца любой — wav, mp3, opus, webm из браузера: сервер перекодирует
его в wav 24 кГц, моно. Короче 3 и длиннее 60 секунд образец не принимается,
вне 8–14 секунд принимается с предупреждением в поле `warnings`. Имя — буквы,
цифры, `-` и `_`; существующий голос перезаписывается только с `replace=true`.

## Голосовой агент: живая речь

`/v1/audio/transcriptions/stream` — WebSocket для живой речи. Клиент шлёт звук
по мере записи, сервер отвечает событиями: человек заговорил, что сказано,
человек договорил. В консоли это кнопка «Диктовка»: реплики там идут абзацами.

```
?language=ru&sample_rate=48000&context=engineering

клиент → двоичные кадры: PCM s16le, моно, частота из sample_rate
клиент → {"type":"end"}                                   — звука больше нет
сервер → {"type":"ready", ...}
сервер → {"type":"speech_start","at":1.63}                — замолчать, если агент говорит
сервер → {"type":"partial","text":"Можешь включить","start":1.13}
сервер → {"type":"final","text":"…","start":1.13,"end":4.28}
сервер → {"type":"turn_check","at":4.28,"probability":0.988,"complete":true}
сервер → {"type":"turn_end","text":"вся реплика","start":1.13,"end":3.97,
          "reason":"model","probability":0.988}               — пора отвечать
сервер → {"type":"done","text":"всё за сессию","duration":14.56}
```

Время — в секундах от начала сессии.

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `language` | определяется | язык речи |
| `sample_rate` | 16000 | частота присылаемого PCM; пересчитывается потоком |
| `context`, `hotwords`, `prompt` | — | контекст распознавания, см. ниже |
| `min_pause` | 0.2 | с тишины, после которых спрашивается модель конца реплики |
| `turn_threshold` | 0.5 | с какой вероятности «закончено» реплика закрывается |
| `max_pause` | 2.0 | с тишины, после которых реплика закрывается в любом случае |
| `interval` | 0.7 | с новой речи между чтениями окна |

**Начало речи** определяет детектор голоса Silero, покадрово, на CPU. Он не ждёт
распознавателя: в прогоне `speech_start` пришёл через 0.3 с после начала речи,
из них 0.1 с — сама нарезка звука кадрами по 100 мс.

**Конец реплики.** Пауза сама по себе — плохой признак: человек замолкает
посреди мысли, подбирая слово. Поэтому на каждой паузе от `min_pause` модель
Smart Turn v3.2 ([pipecat-ai/smart-turn-v3](https://huggingface.co/pipecat-ai/smart-turn-v3),
8 МБ, CPU, 23 мс) слушает реплику и оценивает, закончена ли она по интонации.
Если да — реплика дочитывается, и если текст не обрывается на предлоге, союзе,
заминке или многоточии, приходит `turn_end` с `reason: "model"`. Если нет —
`turn_check` с `complete: false` (и `veto`, если остановил текст), а реплика
закроется после `max_pause` тишины с `reason: "silence"`.

В сквозном прогоне на живых командах `turn_end` пришёл через 0.40–0.46 с после
конца речи. Слабое место — обрыв беглой речи без заминки: по звуку он почти
неотличим от конца, и порог это не лечит, а лишь переносит ошибку из «перебил»
в «ждал зря». Замеры — [experiments/16-voice-agent](../experiments/16-voice-agent/README.md).

Паузу между предложениями модель честно принимает за конец реплики. Если после
`turn_end` скоро пришёл `speech_start`, человек продолжает: агенту стоит
отменить начатый ответ и отвечать на обе реплики сразу.

**Текст.** Окно перечитывается на каждые `interval` секунд новой речи; `partial` —
черновик, он ещё может измениться. Слово окончательно, когда два чтения подряд
с ним согласны, и `final` приходит по предложению — паузы для этого не нужны.

Живая речь идёт мимо очереди. С заданиями она делит только блокировку
распознавателя: пока в очереди распознаётся файл, `partial` и `final`
задерживаются. Детекторы начала и конца реплики работают на CPU и не ждут.

```python
import asyncio, json, websockets

async def listen(pcm_chunks):                  # байты PCM s16le 16 кГц, по ~100 мс
    url = "ws://localhost:8080/v1/audio/transcriptions/stream?language=ru&context=engineering"
    async with websockets.connect(url) as ws:
        async def mic():
            async for chunk in pcm_chunks:
                await ws.send(chunk)
            await ws.send(json.dumps({"type": "end"}))
        asyncio.create_task(mic())
        async for msg in ws:
            e = json.loads(msg)
            if e["type"] == "speech_start":
                ...                            # остановить свой голос
            elif e["type"] == "turn_end":
                ...                            # ответить на e["text"]
```

## Голосовой агент: синтез потоком

Синтез целиком ждёт, пока готов весь ответ, а Qwen3-TTS на RTX 3080 генерирует
медленнее реального времени. Ответ из трёх предложений — 13.6 с звука — готов
только через 26–30 секунд. Агент столько молчать не может, поэтому текст
режется на куски, и каждый отдаётся, как только синтезирован:

| Как | Первый звук | Весь ответ |
|---|---|---|
| целиком | 29.8 с | 29.8 с |
| `stream_format=audio` | 7.0 с | 25.8 с |
| WebSocket, текст токенами в темпе LLM | 7.0 с | 24.9 с |

Резать можно не где угодно. Синтез медленнее воспроизведения, так что между
кусками будут паузы, и им лучше приходиться туда, где слушатель паузу ждёт:

- первый кусок кончается на первой запятой, если перед ней три слова или больше, —
  это то, чего слушатель ждёт дольше всего;
- дальше куски идут по предложениям: «т. е.», «3.5» и «см. выше» не режутся;
- короткое предложение склеивается со следующим, если оно уже известно:
  у каждого вызова есть постоянная цена — «Да.» синтезируется 1.45 с ради 0.64 с звука;
- предложение длиннее 200 символов режется по последней запятой.

**Паузы между кусками на этой карте неизбежны.** В прогоне первый кусок
звучал 3.6 с, второй пришёл через 4.3 с после первого, третий — ещё через 7.9 с.
Поток сокращает ожидание первого звука вчетверо, но сплошную речь даст только
карта, которая синтезирует быстрее реального времени.

### WebSocket для агента

`/v1/audio/speech/stream` принимает текст так, как его пишет LLM, — хоть
по токену, и умеет отмену: человек перебил агента — синтез останавливается
на ближайшем шаге, а уже нарезанный текст выбрасывается.

```
?voice=turgenev&sample_rate=16000&speed=1.0&prepare=false

клиент → {"type":"text","text":"Сейчас я проверю"}     — сколько угодно раз
клиент → {"type":"flush"}                               — озвучить накопленное сейчас
клиент → {"type":"cancel"}                              — перебили: всё выбросить
клиент → {"type":"end"}                                 — текста больше нет
сервер → {"type":"ready","sample_rate":16000,"voice":"turgenev"}
сервер → {"type":"synthesizing","index":0,"text":"Сейчас я проверю расписание,"}
сервер → {"type":"audio","index":0,"text":"…","seconds":3.6,"synth_seconds":6.65}
сервер → двоичный кадр: PCM s16le, моно, sample_rate
сервер → {"type":"cancelled"}
сервер → {"type":"done","chunks":4,"seconds":14.16}
```

Отмена в прогоне сработала за 0.1 с: оборванный кусок не пришёл, следующий
текст озвучился как обычно. Вместе с живой речью это полный контур агента:
`speech_start` из распознавания — `cancel` синтезу, `turn_end` — текст ответа
в синтез.

Синтез потоком идёт мимо очереди: ответ агента, ждущий за длинным файлом, —
не ответ. Он берёт блокировку синтезатора по куску, поэтому уже идущее задание
синтеза всё же задержит его до своего конца.

## Контекст распознавания

Whisper пишет термины точнее, если знает их заранее. Контекст — именованный
профиль на сервере:

| Поле | Что делает |
|---|---|
| `hotwords` | термины, к написанию которых тянется декодер: `Kafka`, а не «кавка» |
| `prompt` | фраза в духе ожидаемой речи; задаёт стиль, термины почти не двигает |
| `replacements` | точные замены после распознавания, целыми словами: `{"гларани": "гуарани"}` |

Встроенный профиль `engineering` — 79 терминов словаря произношений. На 20
фразах с ними доля верно записанных терминов выросла с 60% до 86%, CER упал
с 11.5% до 6.1%. Если заданы и `prompt`, и `hotwords`, сервер передаёт их одной
строкой, подсказку первой: в порядке faster-whisper русская подсказка возвращает
термины в кириллицу.

| Маршрут | Что делает |
|---|---|
| `GET /v1/contexts` | профили, встроенные и свои |
| `GET /v1/contexts/{name}` | один профиль |
| `PUT /v1/contexts/{name}` | создать или заменить: `{"prompt", "hotwords": [...], "replacements": {...}, "note"}` |
| `DELETE /v1/contexts/{name}` | удалить свой |

Контекст принимают `/v1/audio/transcriptions`, `/v1/jobs/transcribe` и живая
речь: `context=имя`, а также `hotwords` через запятую и `prompt` прямо в запросе.
Они складываются с профилем.

```bash
curl -X PUT localhost:8080/v1/contexts/devops -H 'Content-Type: application/json' \
  -d '{"hotwords":["Kubernetes","Helm","Grafana"],"replacements":{"кубер":"Kubernetes"}}'
curl localhost:8080/v1/audio/transcriptions -F file=@созвон.opus -F context=devops
```

Замены делаются только явные. Обратный словарь произношений сюда
не подставляется: он превратил бы любой «лист» в `List`.

## Темп

Параметр `speed` меняет темп **постобработкой готового звука**, а не ручкой модели.
Это не мелочь: замедление средствами модели роняет разборчивость впятеро
(CER 4.6% → 24.9% при переходе к 91 слову в минуту), а постобработка при том же
темпе оставляет её на месте. Подробности — в [ADR 0005](../docs/adr/0005-speaking-rate-via-pauses-and-time-stretch.md).

Осмысленный диапазон — от 0.8 до 1.2. Глубже 0.8 становятся слышны артефакты
растяжения, которых метрика не показывает.

## Системные требования и скорость

### Чтобы работало

Замерено скриптом `scripts/bench.py` на RTX 3080 (10 ГБ) и Core i5-12600KF;
подробности и методика — [experiments/17-benchmarks](../experiments/17-benchmarks/README.md).

| | Видеопамять | Оперативная |
|---|---|---|
| **сервер целиком, распознавание int8_float16** | **≤ 6.1–6.5 ГБ** | 4.6 ГБ |
| сервер целиком, распознавание float16 (по умолчанию) | ≤ 7.1–7.5 ГБ | 4.6 ГБ |
| синтез отдельно, минимум | 4.76–5.13 ГБ | 4.6 ГБ |
| распознавание отдельно, float16 / int8_float16 | 2.35 / 1.38 ГБ | 2.2 ГБ |

Меньшая цифра — для потокового синтеза (куски до 200 символов), большая —
для синхронного вызова с длинным текстом: память растёт с длиной текста.
Для сервера целиком это оценка сверху — минимум синтеза плюс пик распознавания.

Что из этого следует:

- **по этой оценке карта на 8 ГБ подходит**, с `STT_COMPUTE_TYPE=int8_float16` —
  с запасом. На 8-гигабайтной карте напрямую не проверялось: почему — в описании
  эксперимента.
  int8_float16 распознаёт тот же текст слово в слово и с той же скоростью,
  но на 1 ГБ дешевле. Если карта заодно выводит рабочий стол, вычтите то,
  что держит он;
- на карте 10 ГБ и больше сервер займёт до 8 ГБ: PyTorch держит освобождённую
  память про запас. Это занятое, а не необходимое;
- оперативной памяти процесс берёт до 4.6 ГБ, пик — при загрузке весов;
- диск — около 5 ГБ весов в кэше Hugging Face;
- при запуске из исходников — системный `ffmpeg` для opus, mp3 и темпа.

**Под Windows и WSL нехватка видеопамяти не выглядит как ошибка.** Драйвер
по умолчанию добирает недостающее из системной памяти, и на слишком маленькой
карте сервер не упадёт, а станет медленнее. Если скорость ниже таблицы ниже,
проверьте, не упирается ли карта в свой объём.

Без видеокарты сервер работает (`FORCE_CPU=1`, `./voicy up --cpu`), скорость
на процессоре не мерилась.

### Скорость

| | RTX 3080 + i5-12600KF | RTX 5080 |
|---|---|---|
| синтез | ×0.54–0.58 к реальному времени, 136–148 мс на кадр | ×0.4 ([experiments/12](../experiments/12-engine-survey/README.md)) |
| распознавание | ×30–41: 5 минут записи за 7.3 с | быстрее реального времени в разы |
| конец реплики (Smart Turn, CPU) | 23–39 мс на проверку | — |

Скорость синтеза не зависит от длины текста: от 24 до 597 символов — одна и та же.

**Реального времени синтез не достигает ни на одной проверенной конфигурации,
и минимальные требования для ×1 назвать нельзя: дело не в железе.**

Во время синтеза видеокарта загружена в среднем на 36% и берёт 85 Вт из 320,
а один поток процессора занят на 96–100%. На каждый кадр звука — 1/12.6 секунды —
Qwen3-TTS делает проход основной модели и ещё 15 проходов малой, по одному
на каждый кодбук. На 13.5 секунды звука это десятки тысяч мелких операций,
и время уходит на их запуск из Python, а не на счёт: 136–148 мс на кадр
при 79 мс, нужных для реального времени.

Отсюда:

- **более мощная видеокарта не поможет** — на RTX 5080 синтез шёл не быстрее,
  чем на RTX 3080. Сравнение грубое: другая машина и более ранняя версия кода,
  но загрузка карты на 36% говорит то же самое;
- **более быстрый процессор даст проценты, а не нужные разы** — i5-12600KF
  уже из быстрых на одно ядро;
- **путь к ×1 — программный**: CUDA graphs или `torch.compile` для малой модели
  и статический кэш ключей, чтобы кадр запускался одной командой, а не сотнями.
  Не проверялось. flash-attn, который рекомендует документация Qwen, вряд ли
  поможет: внимание в профиле занимает около 4% времени.

Пока синтез медленнее реального времени, для живого разговора берите поток
(`stream_format` или `/v1/audio/speech/stream`): он сокращает ожидание первого
звука вчетверо, но паузы между кусками остаются.

Работа с GPU сериализована очередью: одна модель на 1.7B не выигрывает
от параллельных запросов, а память кончается.

## Что стоит знать

**Прокси.** Если в окружении заданы `HTTP_PROXY` или `HTTPS_PROXY`, клиенты на
httpx (включая официальный клиент OpenAI) пойдут к локальному серверу через прокси
и получат 503. Лечится `NO_PROXY=127.0.0.1,localhost`.

**Ударения.** Qwen3-TTS обучался без разметки ударений и пользовательские знаки
не поддерживает: `+` он произносит вслух как «плюс», диакритика коверкает слово.
Управлять ударением можно только выбором слов. См. [ADR 0015](../docs/adr/0015-stress-control-in-qwen3-tts.md).

**Язык.** Модель заявляет десять языков; проверялся русский.
