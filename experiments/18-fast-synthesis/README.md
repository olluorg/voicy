# 18 — синтез быстрее реального времени

**Вопрос:** можно ли ускорить синтез до реального времени, если упирается он
не в видеокарту.

**Код:** `server/engines/tts_fast.py`
**Скрипты:** `scripts/tts_fast_eval.py` (качество), `scripts/bench.py` (скорость, память)
**Замеры:** `results/results_tts_fast.json`, `results/bench_rtx-3080.json`
**Решение:** [ADR 0020](../../docs/adr/0020-code-predictor-from-cuda-graphs.md)

## Где было время

[Эксперимент 17](../17-benchmarks/README.md) показал ×0.55 к реальному времени
на любой длине текста — 136–148 мс на кадр звука при 79 мс, нужных для ×1.
Видеокарта при этом загружена на 36%, а один поток процессора — на 100%.

Профиль объяснил почему. Кадр звука (1/12.6 с) Qwen3-TTS делает в два этапа:
основная модель (28 слоёв) предсказывает первый кодбук, малая (5 слоёв) —
остальные пятнадцать, по одному. Малую модель основная вызывает через
`generate()` из transformers — 170 раз на фразу в 13.5 секунды, и каждый раз
это 15 проходов по пять слоёв из десятков мелких операций. Запустить такую
операцию из Python дороже, чем её выполнить.

## Что пробовали

| Вариант | На кадр | Скорость |
|---|---|---|
| исходный код | 140–144 мс | ×0.55–0.57 |
| свой цикл вместо `generate()`, без графов | 138 мс | ×0.57–0.58 |
| **свой цикл + CUDA graphs для прохода малой модели** | **51–53 мс** | **×1.50–1.56** |

Фраза из трёх предложений, 13.5 с звука, по два прогона.

Сам `generate()` оказался почти ни при чём: без него выигрыш 2%. Дорого
было количество запусков. CUDA graph записывает проход малой модели
один раз и дальше воспроизводит его одной командой вместо сотен — пятнадцать
графов, по одному на шаг, со статическим кэшем и маской внимания, заданной
заранее: при записи графа transformers не должен ничего считать на процессоре.

Семплирование — как в `generate()`: логиты во float32, температура 0.9,
top-k 50, `multinomial`.

## Совпадает ли звук

Побитово — нет. Статический кэш считает внимание по 16 ячейкам с маской,
исходный — по растущему кэшу, и ядра внимания у них разные. Логиты расходятся
на 0.06–0.25 при размахе 9.5 — одна-две единицы последнего разряда bf16.
Первый проход кадра совпадает до нуля, дальше, где два кандидата почти равны,
выбор иногда переворачивается, и хвост кадра идёт иначе. Совпало 120 кадров
из 169 при одном и том же состоянии генератора случайных чисел — и почти столько же,
121 из 172, при выборе самого вероятного токена: дело не в случайности, а в округлении.

Поэтому проверка статистическая, мерой репозитория ([ADR 0001](../../docs/adr/0001-cer-round-trip-as-the-quality-metric.md)):
10 фраз, по три сида, синтез, распознавание Whisper, ошибки в символах.

| | CER, среднее | CER, медиана | На кадр | Скорость |
|---|---|---|---|---|
| исходный | 2.1% | 0% | 141.5 мс | ×0.55 |
| ускоренный | 2.1% | 0% | 55 мс | ×1.44 |

Все 2.1% — одна фраза, где Whisper записал «восемьдесят» цифрами «80»,
в обоих вариантах одинаково. Остальные 27 синтезов каждого варианта
распознаны без единой ошибки.

## Что это дало агенту

Синтез потоком (`/v1/audio/speech/stream`), тот же ответ из четырёх кусков:

| | До | После |
|---|---|---|
| первый звук | 7.0 с | 3.0 с |
| весь ответ | 24.9 с | 10.7 с |
| паузы между кусками | до 7.9 с | нет |

Паузы исчезли потому, что синтез теперь быстрее воспроизведения: следующий
кусок готов раньше, чем доиграет текущий. После первого звука речь идёт сплошной.

Синхронный синтез того же ответа — 8.6 с вместо 29.8 с.

## Память

Графы держат свой пул памяти: минимум видеопамяти для синтеза — 4.9–5.0 ГБ
против 4.76–5.13 ГБ до ускорения, в пределах точности поиска и разницы путей.
Пик обеих моделей в одном процессе — 8.03 ГБ против 8.09 ГБ.

## Проверено вживую

- синхронный синтез, задания, поток по HTTP и SSE, WebSocket с отменой;
- отмена задания посреди синтеза и синтез сразу после неё;
- синтез и живое распознавание одновременно на одной карте — оба работают,
  синтез при этом ×1.23: карта общая.

Графы записываются при загрузке модели, чтобы за запись не платил первый
запрос. Запись идёт в режиме `thread_local`: распознаватель в другом потоке
может в это время работать на той же карте. `TTS_FAST=0` возвращает исходный путь.

## Что дальше

Куда уходят 52.4 мс кадра теперь (замер с синхронизацией карты вокруг частей):

| | На кадр |
|---|---|
| проход основной модели | 33.4 мс |
| малая модель: 15 графов и семплирование между ними | 14.9 мс |
| прочее: `generate()` основной модели, декодер звука | 4.3 мс |

Основная модель — две трети времени, и она по-прежнему запускается из Python
операция за операцией. Следующий рычаг — тот же приём для неё. Там сложнее:
трёхмерное позиционное кодирование и кэш, растущий на сотни шагов. Поменьше
выигрыш — семплирование внутрь графов малой модели: сейчас между пятнадцатью
графами пятнадцать раз запускаются его пять-шесть операций. Ни то ни другое
не пробовалось.
