# 23 — один voicy.exe на Windows

**Вопрос:** заработает ли тот же бинарник на Windows — с моделями в процессе,
без Python и без установки чего-либо, кроме него самого.

**Код:** `rust/src/setup.rs` (архивы и колёса под Windows, сборка обёртки
через MSVC), `rust/src/cli.rs` (команды в том же бинарнике).

**Ответ:** да. `voicy.exe` — 16 МБ, сам качает библиотеки и модели (7.3 ГБ),
поднимает сервер со всеми четырьмя движками в своём процессе и служит клиентом.
Проверки: 45 из 45 (16 пропущено — форматы, которым нужен ffmpeg).

## Замеры

RTX 3080, Windows 11. Тот же текст, тот же сид, три прогона; звук — 5.04 с.

| | синтез | ×к реальному времени |
|---|---|---|
| Linux (WSL2), тот же бинарник | 1.17–1.35 с | ×3.7–4.3 |
| Windows | 1.54–1.59 с | ×3.2–3.3 |

Распознавание вернуло текст верно; отдельно его скорость на Windows
не мерилась. Расхождение с Linux — в пределах, который объясняется прогревом
и тем, что под Windows карта занята рабочим столом; специально не разбиралось.

## Четыре вещи, без которых не работало

- **В Windows из DLL ничего не видно снаружи без пометки.** Обёртка над
  CTranslate2 собралась, но оказалась пустой: `GetProcAddress` не находил
  ни одной функции. Лечится `__declspec(dllexport)` в исходнике.
- **Имя в `LIBRARY` импортной библиотеки.** Колесо CTranslate2 не содержит
  `.lib`, и она делается из таблицы экспорта DLL. Без строки `LIBRARY` имя
  берётся из имени `.def`-файла, и обёртка искала `ct2.dll`, которой нет.
- **`localhost` на Windows — сначала IPv6.** Сервер слушает IPv4, клиент
  получал отказ. Адрес по умолчанию у клиента теперь `127.0.0.1`.
- **Два OpenMP в одном процессе.** llama.cpp приносит LLVM-овский
  `libomp.dll`, CTranslate2 — Intel-овский `libiomp5md.dll`, и тот, кто
  инициализируется вторым, завершает процесс (`OMP: Error #15`). Копия одного
  под именем другого не помогает: Windows считает её вторым экземпляром.
  `setup` собирает `libomp.dll` как переходник, переадресующий 13 нужных ggml
  символов в Intel-овский рантайм — тогда рантайм один. Переадресацию
  линковщик делает только для символов, которые видит, поэтому в строке сборки
  участвует импортная библиотека Intel-рантайма.

Плюс мелочь: Windows не ищет зависимости библиотеки рядом с ней самой —
каталог движков добавляется в путь поиска (`SetDllDirectoryW`), иначе
`ggml-base.dll` не находит `libomp.dll` в той же папке.

## Два рантайма против одного

У обоих рантаймов есть ключ `KMP_DUPLICATE_LIB_OK=TRUE`, разрешающий
сосуществование; Intel называет его небезопасным и неподдерживаемым. Замер
(тот же текст и сид, три прогона):

| | прогоны | сумма |
|---|---|---|
| один рантайм (переходник) | 1.54, 1.54, 1.59 с | 4.67 с |
| два рантайма (ключ) | 1.54, 1.72, 1.63 с | 4.89 с |

Разница в пределах разброса. Поэтому: переходник — основной путь, он не стоит
ничего; ключ бинарник ставит сам и он выручает там, где компилятора нет.

## Компилятор убран с пути пользователя

Обёртка над CTranslate2 собирается теперь внутрь бинарника (`build.rs`):
импортная библиотека делается из вендоренного списка двадцати символов, которые
обёртка вызывает, а `ctranslate2.dll` помечена отложенной загрузкой — она
понадобится только на первом распознавании. Проверено: с удалённой
`ct2shim.dll` распознавание работает, а с убранной `ctranslate2.dll` бинарник
по-прежнему запускается и отвечает на команды. Заголовки CTranslate2 (77 файлов
тега v4.8.2) лежат в репозитории, чтобы сборка не зависела от сети.

Переходник OpenMP остаётся единственным, что собирается на месте, и он
не обязателен: без компилятора работает ключ, и по замерам выше это ничего
не стоит.

## Что мешает просто отдать файл

Готовых сборок ещё нет — их должен делать CI, вместе с подписью. И без
`ffmpeg` на Windows работает только `wav`: `opus`, `mp3` и `flac` стоит
кодировать в процессе.
