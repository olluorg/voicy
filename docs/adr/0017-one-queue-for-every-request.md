# ADR 0017. Одна очередь на все запросы, диктовка — мимо неё

**Дата:** 2026-09-21
**Статус:** принято

## Контекст

Запрос заказчика: API должно работать асинхронно, каждому запросу — id
и место в очереди, по возможности с webhook. Плюс потоковая расшифровка голоса.

Задания уже были, но только ради прогресс-бара консоли. Каждое запускало свой
поток, а очередью на деле служила блокировка модели. Отсюда четыре проблемы:

- порядок не гарантирован: работу получает тот, кто первым захватил блокировку;
- своё место в очереди не узнать, задание не отменить;
- предела нет: сто запросов — сто потоков, ждущих одну видеокарту;
- совместимые маршруты шли мимо заданий, и их работу не было видно вовсе.

## Решение

**Один воркер, одна очередь, по порядку поступления.** Обе модели делят одну
карту, параллельный запуск не ускоряет, а лишь делит память. Очередь
ограничена (`VOICY_QUEUE_MAX`, 32), сверх предела — 429 с `Retry-After`.

**Совместимые маршруты — тоже задания.** `/v1/audio/speech` и `/v1/audio/transcriptions`
ставят задание и ждут его за вызывающего. Контракт OpenAI не меняется, зато
синхронный вызов больше не обгоняет асинхронные, а его id виден в `X-Job-Id`.
Проверено: синхронный вызов, пришедший третьим, простоял в очереди 8.2 секунды,
пока выполнялись два задания впереди, и лишь потом синтезировал за 6.8 секунды.

**Отмена — между шагами работы.** Синтез проверяет флаг на каждом шаге
декодирования, распознавание — на каждом сегменте. Исключение из счётчика
шагов прерывает генерацию, и следующее задание после этого идёт нормально.

**Webhook несёт сводку, а не звук.** Получатель хочет знать, *что* готово;
звук забирается по ссылке. Повтор с растущими паузами, подпись HMAC по желанию.

**Задания живут в памяти.** Перезапуск сервера их забывает. Хранить на диске
пока незачем: сервер живёт долго, а готовое забирают в пределах минут.
Если понадобится — сводка уже сериализуется в JSON целиком.

**Диктовка идёт мимо очереди.** WebSocket `/v1/audio/transcriptions/stream`
не может ждать за длинным синтезом и оставаться живым. Он берёт блокировку
распознавателя между заданиями. Синтез её не держит, поэтому очередь из синтеза
диктовку не тормозит, очередь из распознавания файлов — тормозит.

## Как устроен поток

Whisper читает окно целиком, потоковым его делает обвязка. Незаконченная фраза
перечитывается на каждую секунду нового звука с `beam_size=1` и уходит
черновиком (`partial`). Фраза закрывается, когда детектор голоса Silero
из faster-whisper слышит паузу от 0.6 секунды. Тогда она перечитывается
с `beam_size=5` и уходит окончательной (`final`). Хвост уже сказанного
передаётся подсказкой, чтобы фраза, разорванная паузой, сохраняла написание.

Без пауз окно режется на 20 секундах по последней найденной паузе.
На 38 секундах синтезированной речи с короткими паузами между предложениями
первая окончательная фраза пришла на 21.6 секунде, то есть закрытие по длине
окна работает, но запаздывает. У живой речи паузы длиннее.

Окно хранится в частоте клиента и пересчитывается в 16 кГц целиком на каждом
проходе. Пересчёт кусков по 100 мс поодиночке давал бы щелчки на стыках.

## Последствия

- `/v1/jobs/speech` отвечает 202 вместо 200, в ответе — полная сводка задания.
- События заданий раздаются всем подписчикам: следить за одним заданием могут
  несколько клиентов. Раньше второй клиент отбирал события у первого.
- Место в очереди в событиях называется `queue_position`, а не `position`:
  у распознавания `position` уже значит «до какой секунды файла дошли».
- Загрузка голоса перекодирует любой формат в wav 24 кГц. Раньше браузерный
  webm сохранялся под расширением `.wav` как есть.
