# ADR 0024. Движки — отдельный крейт voicy-core, сервер — обёртка над ним

**Дата:** 2026-09-28
**Статус:** принято

## Контекст

Программе на Rust, которой нужна речь, приходилось поднимать `voicy serve`
и ходить к нему по HTTP: второй процесс, порт, сериализация звука туда и обратно.
При этом движки на Rust ([ADR 0022](0022-rust-migration-and-hardware.md))
уже исполнялись в процессе сервера и от HTTP не зависели — зависели лишь
модули вокруг них: ошибки в формате OpenAI, tokio, глобальные настройки
из переменных окружения.

## Решение

`rust/` — workspace из двух пакетов. `rust/core` (`voicy-core`) — библиотека:
движки, кодеки и темп, чтение и запись звука, подготовка текста, нарезка текста
для синтеза потоком, голоса, `setup` (фича `download`). Сверху — небольшой API:
`Tts`, `Stt`, `Vad`/`Turn`, типизированный `Transcript`. `rust/` остаётся
пакетом `voicy` — сервер и CLI; модули ядра он импортирует под прежними
именами (`use voicy_core::{native, …}`), поэтому его код почти не изменился.

Крейт собирается в пакет сам по себе, без остального репозитория, — чтобы его
можно было выложить на crates.io и чтобы git-зависимость не зависела от
раскладки репозитория.

- **Только родные движки.** Python-хост требует репозитория и Python; в
  библиотеке его нет. Кому он нужен — тому сервер.
- **Узкий публичный API.** Привязки к llama.cpp, CTranslate2 и ONNX Runtime
  (`native`) и кодеки (`encode`) — внутренние: снаружи их видит только сервер,
  через фичу `internal`, и меняться они вправе вне semver. Вспомогательное
  для CLI в `setup` скрыто из документации.
- **Блокирующий API, async — фичей.** Движки блокирующие по природе (держат
  видеокарту, пока считают); навязывать tokio программе, которая его не
  использует, незачем. Фича `tokio` даёт `*_async` через `spawn_blocking`.
- **Окружение — только по просьбе.** `Default` у настроек от окружения не
  зависит; то, что читает сервер (`TTS_GGUF_TALKER`, `FORCE_CPU`,
  `STT_COMPUTE_TYPE`, …), читают `TtsConfig::from_env` и `SttConfig::from_env`.
  Исключение — место кэша (`VOICY_CACHE`): это общий с `voicy setup` адрес,
  и из кода его перекрывает `use_dirs`, один раз на процесс, потому что
  рантаймы, раз загрузившись, остаются.
- **Сообщения — через `log`.** Сервер ставит логгер, который печатает их
  в stderr в прежнем виде (`voicy: …`, `setup: …`). Вопрос «[Y/n]» и полоса
  прогресса установщика — не сообщения, а его интерфейс в терминале; полоса
  рисуется, только если stderr — терминал.
- **Поставляемые голоса и словарь — в крейте** (`rust/core/assets`):
  `include_bytes!` не выходит за пределы пакета. `server/voices` стал тем, чем
  уже был `server/contexts`, — данными пользователя вне git; оба сервера
  наполняют пустой каталог голосами из поставки. Docker-том `voicy-voices`
  по-прежнему смонтирован в `/app/server/voices`, образ кладёт туда те же голоса.
- **Ударения в ядре синхронные**, сервер уводит их в `spawn_blocking`.
- **Одна версия на двоих.** Сервер почти не меняется без ядра, так что отдельная
  нумерация дала бы лишь путаницу. Версия задана один раз — `[workspace.package]`
  в `rust/Cargo.toml`; тег `v*` выпускает бинарники и публикует крейт на
  crates.io (`release.yml`), сверив тег с версией. Выпуск без изменений в ядре —
  тоже новая версия крейта, и это приемлемо.

### Обёртка CTranslate2 на Windows

Раньше `build.rs` вкомпилировал обёртку в бинарник, а `ctranslate2.dll`
подключалась ключом `/DELAYLOAD`, чтобы `voicy.exe` запускался до `voicy setup`.
Ключ компоновщика Cargo передаёт только целям своего пакета: после разделения
его пришлось бы повторять в `build.rs` каждой программы, встроившей крейт.

Теперь `build.rs` собирает обёртку отдельной `ct2shim.dll` (импортная
библиотека для CTranslate2 по-прежнему делается из вендоренного списка
символов), её байты едут внутри крейта, а при первой загрузке Whisper она
кладётся в каталог библиотек движков под именем с хешем содержимого и грузится
через `libloading` — так же, как `libct2shim.so` на Unix. Программа CTranslate2
не импортирует вовсе, и ничего от того, кто её собирает, не требуется. Имя по
хешу — чтобы не перезаписывать DLL, открытую другим процессом, и чтобы две
сборки из разных исходников не мешали друг другу. На скорость это не влияет:
вызов через указатель на функцию, двадцать вызовов на отрезок в 30 с.

## Последствия

- Движки — тот же код, что был: перенесён, а не переписан. Проверки API
  (67 из 67) проходят для обоих серверов, родные тесты — тоже; сервер на родных
  движках синтезирует и распознаёт как раньше.
- CI проверяет, что `cargo package -p voicy-core` собирается, на Linux
  и Windows; на Windows это заодно сборка `ct2shim.dll`.
- Кто держал свои голоса в `server/voices` рядом с поставляемыми: после
  обновления поставляемые файлы уходят из git; `git pull` откажется, если
  `voices.json` правили, — его нужно отложить и вернуть после.
