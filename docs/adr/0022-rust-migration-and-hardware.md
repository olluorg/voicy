# ADR 0022. Переезд на Rust — по слоям, и на любом железе

**Дата:** 2026-09-22
**Статус:** принято; выполняется по шагам ниже

## Контекст

Сервер отвечает на вопросы, ради которых делался, и дальше важны три вещи:
скорость, память и простая доставка. Сейчас доставка — это Python 3.12, torch
и несколько гигабайт зависимостей, а образ собирается только под x86-64 с CUDA.

Требования к железу:

- **не только NVIDIA:** видеокарты Intel Arc и работа на одном процессоре —
  такие же цели, как CUDA;
- **не только x86:** процессоры ARM64 поддерживаются наравне;
- **не только Linux:** Windows на x86-64 и на ARM64, Linux, macOS. На macOS
  это и своё железо — Apple silicon с видеокартой через Metal;
- **и ни шагу назад:** ради охвата нельзя менять библиотеку или слой на менее
  производительные. Что уже работает быстро, остаётся быстрым.

Сейчас код знает только CUDA и процессор: устройство определяется через torch
(`engines/device.py`), ARM не проверялся, Intel Arc и Apple не поддержаны.
Проверена одна система — Linux x86-64 (WSL2). Сервер из исходников на Windows
и macOS не запускался, а CLI написан на Python и управляет процессом сервера
по-юниксовски: pid-файлом и сигналами.

Слои и швы между ними — на схеме в README (`docs/architecture.svg`):
HTTP API, контракт движков (ADR 0021), среда исполнения, устройство. Любой
слой меняется, не трогая соседей, — это и делает переезд постепенным.

## Решение

**Переезжать по слоям, и после каждого шага версия рабочая.** Rust вытесняет
Python участок за участком, начиная с тех, где риск меньше.

1. **Проверки API и учебный движок.** Набор проверок ходит к серверу только
   по HTTP и WebSocket, поэтому одинаково проверяет любую его реализацию.
   Учебный движок вместо речи отдаёт тон, вместо распознавания — известный
   текст: проверки идут за секунды, без видеокарты, в CI на всех целевых
   системах — Linux, Windows и macOS, на x86-64 и ARM64.
   Запуск — одной командой, результат — один файл отчёта с описанием железа:
   прогоны на чужих машинах делают люди, а не CI.
2. **Слой устройств в контракте.** Движок объявляет, какие устройства умеет;
   выбор — `VOICY_DEVICE=auto|cuda|intel|cpu`. На CUDA всё остаётся как есть.
   Первый замер на Intel Arc — Qwen3-TTS на PyTorch XPU, ещё до Rust.
3. **CLI на Rust.** Он говорит с сервером только по HTTP; клиенты и код-агенты
   получают один бинарник под каждую платформу.
4. **Движки в отдельном процессе.** Python-движки отвечают серверу по протоколу,
   повторяющему контракт; нынешний сервер зовёт их через него. Язык ещё не
   меняется — меняется граница, и её ошибки ловятся на знакомом коде.
5. **Сервер на Rust** поверх того же процесса движков. Какое-то время обе
   реализации проходят один набор проверок; Python-сервер остаётся запасным
   на один выпуск.
6. **Родные движки по одному:** детектор голоса, конец реплики, распознавание,
   синтез. Каждый выбирается переменной, Python-вариант живёт рядом, пока родной
   не прошёл замеры на каждом целевом железе.
7. **Образы под все платформы** и сервер без Python. Процесс Python-движков
   остаётся необязательным: через него новая модель, у которой есть только
   код на PyTorch, подключается в тот же день.

**Для каждого железа — свой самый быстрый путь, универсальный — запасной.**
Движок может иметь несколько сред исполнения и выбирает по устройству, так же
как сейчас Qwen включает CUDA graphs только на CUDA. Общий знаменатель
по умолчанию не выбирается никогда.

- **NVIDIA:** остаётся то, что есть и измерено: faster-whisper (CTranslate2),
  Qwen3-TTS с CUDA graphs (ADR 0020). Замена — только если на той же карте
  она не хуже по скорости, памяти и CER.
- **Intel Arc:** то, что Intel поддерживает лучше всего. Первый кандидат для
  синтеза — PyTorch XPU: тот же код Qwen, что на NVIDIA. Для распознавания
  CTranslate2 карту Intel не видит, так что нужен другой путь — OpenVINO или
  whisper.cpp (SYCL, Vulkan); выбор по замеру на карте.
- **Apple silicon:** то, что Apple поддерживает лучше всего, — кандидаты
  PyTorch MPS, MLX, GGML на Metal; выбор по замеру.
- **Процессоры x86 и ARM:** что быстрее на процессоре; CTranslate2 работает
  на обоих и уже используется.
- **GGML и ONNX Runtime** — там, где своего быстрого пути нет, и как основа
  родных движков на Rust — если на данном железе они не уступают прежнему.

Ускорения под одно железо — CUDA graphs сейчас, свои ядра позже — не
«надстройка, от которой можно отказаться», а путь для этого железа.

**Порог для каждого шага:** набор проверок зелёный; на каждом железе, где
вариант заявлен, он не хуже прежнего ни по скорости, ни по памяти, ни по CER
(`scripts/engine_eval.py`, `scripts/bench.py`) — и лучше хотя бы в чём-то,
иначе замена не нужна. Это касается и сервера: Rust-сервер заменяет
Python-сервер, только если не медленнее его. Не прошёл — остаётся прежний
вариант.

## Где проверяется железо

| Железо | Где |
|---|---|
| NVIDIA, x86-64 | машина автора: RTX 3080 10 ГБ, Linux (WSL2) |
| Intel Arc | машина брата автора: Arc A750 8 ГБ, Windows; прогон по команде, отчёт файлом |
| Apple silicon | живого устройства пока нет |
| процессоры | CI GitHub: Linux x86-64 и ARM64, Windows x86-64 и ARM64, macOS ARM64 — без моделей, с учебным движком |

У A750 8 ГБ, и Qwen3-TTS с Whisper вместе там тесно: по замерам на NVIDIA
серверу целиком нужно до 7.4 ГБ, с распознаванием в int8 — до 6.4 ГБ
(experiments/17). Это первое, что проверит прогон на Arc.

## Отвергнуто

**Переписать сразу всё.** Без набора проверок правильность нового сервера
держалась бы на ручных прогонах, а сломанное было бы видно только клиентам.

**Встроить Python в Rust-сервер (PyO3).** Доставка осталась бы прежней —
тот же Python с torch внутри, — а блокировка интерпретатора легла бы на сервер.

**Одна среда исполнения на всё железо.** Проще в сборке, но на каждом железе
она уступает тому, что это железо умеет лучше всего: на NVIDIA — нынешним
CTranslate2 и CUDA graphs. Охват не покупается скоростью.

**candle как основа.** Удобнее всего из Rust, но видеокарт Intel не поддерживает.
