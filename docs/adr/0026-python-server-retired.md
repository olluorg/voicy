# ADR 0026. Python-сервер убран: сервер — только бинарник на Rust

**Дата:** 2026-10-02
**Статус:** принято

## Контекст

Шаг 5 [ADR 0022](0022-rust-migration-and-hardware.md) обещал держать
Python-сервер запасным один выпуск после того, как его заменит Rust. Так
и вышло: с 1.9 бинарник на Rust лежит в выпусках, с 1.10 он же стоит в образе
docker ([ADR 0025](0025-docker-image-on-rust.md)). Python-сервер (`server/app.py`
и ещё пятнадцать модулей на FastAPI) оставался только за `./voicy up --source`,
то есть там, где не было docker.

Две реализации одних маршрутов обходились дорого. Каждое изменение API
делалось дважды, и обе версии проверялись одним набором проверок. Пользователь
без docker получал более медленный сервер: синтез ×1.4 против ×3.8, первый
звук в потоке 3 с против 0.7, видеопамяти 9.3 ГБ против 5.7 (experiments/20, 22).
А в README приходилось объяснять, какой сервер работает где.

## Решение

**Сервер — только бинарник на Rust.** Python-сервер удалён: маршруты, очередь,
задания, живая речь, синтез потоком, голоса, контексты, ключ, webhook.

- **`./voicy up` без docker запускает бинарник.** CLI ищет его в `VOICY_BIN`,
  в `rust/target/release/` и в PATH. Найденный бинарник ставит библиотеки
  и модели (`voicy setup`; на полном кэше это мгновенно и без сети) и поднимает
  сервер своей командой `up`. pid и журнал лежат в `<кэш>/run/`, остановка —
  `./voicy down`. `--install` собирает бинарник, если его нет, и качает
  модели не спрашивая. Флаг `--source` оставлен как синоним `--native`,
  чтобы прежние сценарии не ломались.
- **Python-движки остаются** (`server/engines/`), как и предполагал шаг 7
  ADR 0022. Сервер поднимает их дочерним процессом, только если выбран
  движок, которого нет в родном виде: `TTS_ENGINE=qwen3-tts` (PyTorch),
  `espeech`, учебные движки для проверок. Через них же сервер дочитывает
  форматы, которых не читает сам (`engines/audio.py`, PyAV).
- **Там, где родных библиотек нет**, то есть на macOS и ARM64, бинарник
  работает с движками на Python. `setup` там отказывает, а `./voicy up`
  говорит об этом и всё равно поднимает сервер.
- **В репозитории остаются данные сервера**: консоль (`server/static/`),
  голоса и профили контекста (`server/voices/`, `server/contexts/`). Пути
  те же, что раньше, и тома docker не меняются.
- **Проверки идут против бинарника.** `tests/` поднимает
  `rust/target/release/voicy` (другой — `VOICY_RUST_BIN`) с учебными движками
  в дочернем Python. Переменной `VOICY_IMPL` больше нет. Зависимости проверок —
  numpy, PyAV и websockets: FastAPI и uvicorn больше не нужны.
- **CI собирает бинарник на каждой платформе.** Linux и Windows на x86-64
  обязаны быть зелёными. ARM64 и macOS прогоняются, но их сбой не валит
  прогон, пока сборка под них не отлажена.

## Последствия

- Одна реализация API вместо двух; каждый пользователь получает быстрый сервер.
- На машине без Rust сервер из репозитория не поднять, пока нет бинарника:
  его нужно собрать (`./voicy up --install`: Rust, g++, cmake) или скачать
  из выпусков. Python для этого не нужен.
- **macOS и ARM64 теряют проверенный путь.** Python-сервер проходил там
  проверки с учебными движками в CI. Бинарник под эти системы ещё не собирался,
  и пока сборка не отлажена, его сбой в CI виден, но не обязателен. Это
  первое, что стоит сделать по шагу 7 ADR 0022.
- Скрипты, которые мерили Python-движки напрямую (`scripts/bench.py`,
  `tts_fast_eval.py`, `turn_eval.py`), раньше брали части сервера: голос
  по умолчанию, нарезку текста, список «висящих» слов. Теперь у них свои
  копии: `scripts/shipped_voice.py` и список в `turn_eval.py`, тот же, что
  в `rust/src/live.rs`.
- Прежний `.venv` с torch для сервера больше не нужен. Он пригодится, только
  если выбран движок на Python.

## Отвергнуто

**Оставить Python-сервер ещё на выпуск.** Шаг 5 ADR 0022 этот выпуск уже
дал. Ещё один означал бы снова писать каждое изменение API дважды, а
пользователь без docker снова получал бы медленный сервер.

**Переписать `./voicy` на Rust или сделать его обёрткой бинарника.** CLI
на стандартной библиотеке Python работает как клиент любого сервера, даже
удалённого, и ему не нужна сборка. Команды бинарника те же, так что можно
пользоваться любым из двух.
