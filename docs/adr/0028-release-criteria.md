# ADR 0028. Критерии выпуска: что не пускает версию к пользователям

**Дата:** 2026-11-03
**Статус:** принято, внедряется по шагам в конце. Пороги из таблицы —
предварительные, их проверит первый прогон.

## Контекст

С 1.5.0 по 1.10.0 вышло 8 версий за шесть дней, и выпуск почти ничем не защищён:

- `release.yml` запускает только `cargo test`. Проверки API (`python -m tests`)
  в нём нет, а шаг запуска бинарника заканчивается `|| true` и упасть не может.
- `docker.yml` публикует образ по тегу независимо от проверок, а `latest`
  обновляет при каждом пуше в `master`.
- `scripts/acceptance.py` меряет сервер на настоящих моделях, но запускается
  вручную и ничего не блокирует. Его порог скорости — «быстрее реального
  времени», при заявленных ×4 на RTX 3080: падение до ×1.1 он пропустит.

Цена этого уже известна. 2026-09-29 вышел `av` 19, без параметра
`metadata_errors`, а `av` у нас не закреплён. Распознавание через Python-движки
сломалось, и `tests.yml` на `master` с тех пор красный: 13 из 67 проверок на
всех платформах, где доходит до них (windows-arm64 не собирается вовсе, это
отдельная история). Сигнал был, но ни на что не влиял. Родные движки бинарника
и образа это не задело: Python им не нужен.

## Решение

Выпуск определяется тремя уровнями проверок. Цель — не защита от злого умысла,
а защита от забывчивости: проект ведёт один человек, и критерии должны быть
настолько дешёвыми, чтобы их не хотелось обходить.

### 1. Автоматически, на каждый тег

Блокируют выпуск бинарников, образа и крейта:

- `cargo test` и `python -m tests` на Linux x64 и Windows x64 — на коммите тега,
  а не по статусу `master`: пуши только с документацией `tests.yml` не запускают.
  ARM64 и macOS на теге не запускаются (ADR 0022): отменённая задача красит весь
  запуск и при `continue-on-error`, а машин с macOS GitHub иногда не находит;
- `cargo package -p voicy-core`;
- бинарник запускается без кэша: `--version` обязан пройти. `status` без сервера
  всегда завершается с ошибкой, поэтому он остаётся только для журнала;
- `cargo audit` без известных уязвимостей. Предупреждения о заброшенных крейтах
  выпуск не останавливают.

Проверки идут только на теге: новая уязвимость не должна красить чужие PR.

### 2. На видеокарте, если менялось то, что влияет на звук

`scripts/release-check` поднимает сервер, запускает приёмку и создаёт
аннотированный тег, в описание которого кладёт таблицу, машину и числа. Описание
тега и так уходит в заметки к выпуску, поэтому числа видны пользователям, а база
для сравнения — описание предыдущего тега. Отдельные файлы отчётов не нужны.

Приёмка нужна, если с прошлого тега менялись `rust/core/**`, `rust/Cargo.lock`,
`rust/src/speak.rs` или голоса. Иначе скрипт так и пишет в описании тега, а CI
проверяет это по тому же списку путей: версия, которая трогает только API или CLI,
не ждёт прогона, но и обойти его пометкой нельзя.

| Что меряем | Порог сейчас | Блокирует выпуск |
|---|---|---|
| CER обратного распознавания | ниже 5% | выше 5% или хуже прошлого выпуска более чем на 1 п.п. |
| Скорость синтеза | быстрее реального времени | хуже прошлого выпуска более чем на 20% |
| Первый звук в потоке | до 3 с | дольше 1,5 с |
| Видеопамять после серии запросов | рост меньше 1 ГБ | без изменений |
| Остальные строки приёмки | свои | без изменений |

Первый замер (v1.11.0 без исправления потока, RTX 3080): CER 2,05%, длинный текст
×3,1, первый звук 1,2 с. Порог в 1 с, как заявлено в `AGENTS.md`, не проходила ни
старая сборка, ни новая.

Сравнение с прошлым выпуском имеет смысл только на той же машине: на другой
сравниваются лишь абсолютные пороги. Порог CER в 1 п.п. под вопросом: в ADR 0009
разброс между конфигурациями был сопоставим с разбросом самого замера. Если два
прогона одного коммита разойдутся сильнее, порог нужно поднять, иначе он будет
срабатывать на шум.

### 3. Вручную, по тому, что изменилось

| Изменилось | Что сделать |
|---|---|
| модель, движок, разметка текста | прослушать контрольные фразы: CER не слышит дефекты вроде обрубленного начала фразы (ADR 0009) |
| `setup.rs`, версии библиотек | чистая установка на Linux и Windows |
| голоса | каждый голос синтезирует контрольную фразу |
| API | запись в описании тега; ломающее изменение — новая мажорная версия |
| только документация и эксперименты | выпуск не нужен |

### `latest`

Тег `latest` образа обновляется только при выпуске, а не при пуше в `master`:
`compose.yml` запускает именно его, и сейчас каждый пуш сразу попадает к
пользователям. Кому нужен `master` — для этого уже есть образ с тегом ветки.

## Отвергнуто

**Self-hosted runner с видеокартой.** Надёжнее, потому что не зависит от памяти,
но его надо поддерживать, а открывать машину заданиям из CI ради одного
разработчика — лишний риск.

**Проверять в CI статус `master`.** Пуши только с документацией проверки не
запускают, так что статус мог бы относиться к другому коммиту.

**Приёмка на каждый выпуск.** При нынешнем темпе её начнут обходить. Важен не
номер версии, а что изменилось: патч в движке прогона требует, новая минорная
версия с правкой CLI — нет.

**Запись отчёта файлом в репозиторий.** Коммит с отчётом — уже другой коммит, чем
тот, что проверялся.

## Последствия

- Выпуск с изменениями в движке теперь требует машины с видеокартой и времени на
  прогон. Срочное исправление в движке тоже его ждёт.
- Первый прогон `cargo audit` нашёл 10 уязвимостей в выпущенной v1.10.0
  (`rustls`, `rustls-webpki`, `webpki-roots`, `zip`), их закрыла v1.11.0. Остаются
  два предупреждения: `audiopus_sys` и `paste` заброшены.
- Приёмка на CPU не сойдётся с порогом первого звука, поэтому выпуск с изменениями
  в движке на машине без видеокарты невозможен. Так и задумано.
- Пользователи `compose.yml` будут получать обновления реже, зато только
  проверенные.

## Внедрение

1. Влить исправление `av` в `master` и убедиться, что он зелёный: пока он красный,
   уровень 1 будет блокировать всё. Сделано.
2. Подключить `tests.yml` к `release.yml` и `docker.yml` через `workflow_call`,
   строго проверять `--version`, добавить `cargo audit`; `cargo package` уже в
   `tests.yml`.
3. Перевести `latest` на выпуски.
4. Написать `scripts/release-check` и ужесточить пороги в `acceptance.py`; два
   прогона одного коммита покажут разброс и окончательные значения.
5. Добавить в `release.yml` проверку описания тега.
