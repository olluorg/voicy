# ADR 0025. Образ docker — сервер на Rust

**Дата:** 2026-09-29
**Статус:** принято; Python-сервер, оставленный здесь для запуска из исходников, убран в [ADR 0026](0026-python-server-retired.md)

## Контекст

С 1.9 в выпусках два сервера: бинарник на Rust ([ADR 0022](0022-rust-migration-and-hardware.md),
[ADR 0024](0024-engines-as-a-library.md)) и Python-сервер в образе docker —
`nvidia/cuda` 12.8, torch, uvicorn. Маршруты у них одни, проверки одни,
а поведение и скорость — разные: синтез на Rust почти втрое быстрее (×3.8
против ×1.4), видеопамяти в полтора раза меньше (5.7 ГБ против 9.3; experiments/20, 22). Пользователь docker получал более медленный
сервер и образ на десяток гигабайт.

## Решение

В образе — бинарник `voicy`, собранный из того же коммита многоступенчатой
сборкой, и библиотеки его движков. Python-сервер остаётся в репозитории для
запуска из исходников, в образ он не входит.

- **Библиотеки — в образе, модели — в томе.** Версии библиотек закреплены за
  бинарником (`setup.rs`), с новым образом должны приходить новые; обёртку над
  CTranslate2 на Linux собирает `voicy setup` g++, и он нужен только на этапе
  сборки. Модели не зависят от версии и весят восемь гигабайт — они в томе
  `/cache`, как и раньше веса Python-сервера.
- **Основа — `ubuntu:24.04`, не `nvidia/cuda`.** CUDA 13 и cuDNN приходят
  с библиотеками движков; от хоста нужен только драйвер (через NVIDIA Container
  Toolkit). Цена — драйвер 580 и новее вместо 570 для CUDA 12.8.
- **Модели качает сам контейнер при старте**: `voicy setup models --yes`, потом
  `voicy serve`. На полном томе setup выходит сразу и в сеть не ходит (проверено
  с нерабочим прокси). Пока идёт первая загрузка, сервер не отвечает — у Python-
  сервера `/health` отвечал раньше, — поэтому `start-period` проверки здоровья —
  час, и столько же по умолчанию ждёт `./voicy up`.
- **Без проброшенной видеокарты — процессор, а не падение.** Так вёл себя
  Python-образ. Сервер на Rust спрашивает у рантайма CUDA из своих библиотек,
  сколько устройств видно; при нуле оба движка грузятся на процессоре и один раз
  об этом говорят. `FORCE_CPU=1` теперь относится и к синтезу — раньше только
  к распознаванию, и синтез без GPU падал в ONNX Runtime. Где рантайма CUDA нет
  вовсе, GPU не запрещается: там может быть видеокарта другого рода.
- **Тома и пути прежние**: `/cache`, `/app/server/voices`, `/app/server/contexts`;
  формат голосов у серверов общий. Каталог голосов без индекса сервер наполняет
  поставляемыми голосами, в том числе заданный через `VOICY_VOICES_DIR`, —
  иначе папка хоста, подключённая вместо тома, осталась бы без голосов.
- **SIGTERM.** Сервер в контейнере — процесс №1, а ему сигнал без обработчика
  не доставляется: `docker stop` ждал бы десять секунд и убивал. Теперь сервер
  выходит по SIGTERM и Ctrl+C сразу.

## Замеры

Бинарник, RTX 3080 и Core i5-12600KF (WSL2), прогретая модель, фраза на 5.6 с:
на GPU синтез 1.6 с (×3.5 к реальному времени), на процессоре 10–13 с
(примерно вдвое медленнее реального времени). Распознавание верное в обоих случаях.

## Последствия

- Образ меньше и быстрее, и это тот же сервер, что в выпусках: одна реализация
  на пользователя вместо двух.
- Хостам с драйвером старше 580 образ с GPU не подойдёт — только на процессоре
  или прежний образ `ghcr.io/olluorg/voicy:1.9`.
- В томе `/cache` от прежнего образа остаётся `huggingface/` (около пяти
  гигабайт) — его можно удалить.
- Модели, которые умеет только Python-сервер (`TTS_ENGINE=qwen3-tts` и т. п.),
  в образе недоступны.
- CI собирает образ и проверяет его перед публикацией: бинарник запускается,
  библиотеки и голоса на месте, зависимостей хватает. С моделями и GPU образ
  в CI не запускается.
